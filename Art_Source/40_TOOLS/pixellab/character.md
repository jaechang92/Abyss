## 7. 캐릭터 경로 — **환경과 다른 도구다** (2026-09-10 스키마 조사)

⚠️ **이 절은 스키마만 읽고 적은 것이다. 아직 한 번도 안 호출했다.**
`environment.md` §6 에서 「채워 놓은 칸이 여섯 개 틀렸다」를 겪었으므로, 아래도 첫 실호출에서 검증할 것.

환경은 `create_image_pro` + `create_sidescroller_tileset` 둘이었다. 캐릭터는 **세 도구**이고
모델·비용·규약이 전부 다르다. **환경의 앵커 규약을 그대로 옮길 수 없다.**

| 도구 | 하는 일 | 비용 | 크기 |
|---|---|---|---|
| `create_character` | 8방향 회전 캐릭터를 만든다 | standard **1** · v3 **2~9** · pro **20~40** | 기본 48 · standard/pro 최대 **128** · v3 **256** |
| `create_character_state` | **같은 인물의 변형**(옷·자세·상태) | **20~40** | 원본 캔버스 (override 로 키움) |
| `animate_character` | 애니메이션 | template **1/방향** · v3 **~1/방향**(≤96px) · pro **20~40/방향** | — |

### 🔑 `create_character_state` 가 폼 4종 규약과 정확히 대응한다

스키마가 이렇게 적어 두었다:

> *이것은 **언제나 같은 인물의 얼굴과 정체를 유지한다** — 「늙음」·「부상」·다른 직업 같은
> 편집에도 그렇다. 이 캐릭터의 **변형**을 만들지 새 캐릭터를 만들지 않는다.*

`10_BIBLE/08-silhouette §4` 와 폼 주제 파일 ①이 *「넷은 다른 캐릭터가 아니라 **같은 사람이
형태를 바꾼 것**」*이라고 못박아 두었다. **도구가 그 규약을 그대로 갖고 있다.**
→ 폼 하나를 앵커로 만들고 나머지 셋을 state 로 파생시키는 것이 이 도구의 결대로 가는 길이다.

⚠️ 다만 **state 는 20~40 gen 이다.** 셋이면 60~120. 환경 파생(호출당 4장 후보)과 달리
**후보를 여러 장 못 받는다** — 큐레이션 공정이 여기서는 「다시 뽑기」가 된다.

### 🔴 횡스크롤인데 도구는 8방향을 만든다

`n_directions` 는 **4 또는 8만** 받는다. 우리에게 필요한 것은 좌우 2방향(사실상 1방향 +
좌우 반전)인데 **최소가 4다.** `view="side"`(눈높이)가 따로 있으므로 시점은 맞출 수 있지만
**방향 수는 못 줄인다** — 안 쓰는 방향에도 값을 낸다.

💡 `animate_character` 는 다르다 — `directions` 로 **원하는 방향만** 고를 수 있다.
애니메이션이 비용의 대부분이므로 **거기서 줄이면 된다.**

🔑 **2026-09-10 사용자 확인 — 방향은 하나면 된다.**
우측 방향만 생성하고 **Unity 에서 flip 으로 좌향을 만든다**(`SpriteRenderer.flipX`).
좌우를 각각 뽑을 이유가 없다 — 픽셀 아트 횡스크롤의 표준 방식이다.

```
애니메이션 비용   9상태 x 4폼 = 36개
  좌우 2방향      ~72 gen
  우측 1방향      ~36 gen   <- 이쪽. 절반이다
```

⚠️ **flip 이 안 맞는 자리가 있는지는 확인할 것** — 폼 넷이 전부 한 손 무기라
flip 하면 「대검이 오른손에서 왼손으로」 바뀐다. 횡스크롤에서 이것을 문제 삼는 게임은
거의 없지만, **UI 초상·도감처럼 한 방향으로만 보이는 자리**는 flip 안 한 쪽을 쓴다.

### 🔴 상태 9종이 템플릿과 부분적으로만 맞는다

```
우리 상태 (PlayerAnimationIds SoT)   템플릿에 있는가
  Idle          fight-stance-idle-8-frames · breathing-idle   ✅
  Run           running-4/6/8-frames                          ✅
  Jump          jumping-1 · jumping-2 · two-footed-jump        ✅
  Fall          ❌ 없다 — v3 (action_description) 로
  Dash          running-slide 가 가깝다                        ⚠️
  AttackLight   cross-punch · lead-jab (맨손이다)              ⚠️
  AttackHeavy   surprise-uppercut · roundhouse-kick (발차기)   ⚠️
  Hit           taking-punch                                  ✅
  Dead          falling-back-death                            ✅
```

⚠️ **공격 템플릿이 전부 맨손·발차기다.** 우리 폼은 대검·활·방패·투척이라 템플릿을 그대로
쓰면 **무기가 안 움직인다.** 공격 4개는 v3(`action_description`)로 가야 할 가능성이 크다.
📌 그런데 무기가 실루엣의 전부다(`08-silhouette §4`) — **무기가 안 움직이면 폼이 안 읽힌다.**

### 비용 산수 (지어낸 것 — 실호출로 검증할 것)

```
앵커 캐릭터 1개   v3         2~9
폼 3종 state      20~40 x3   60~120
애니메이션        9상태 x 4폼 = 36개
                  template/v3 ~1 gen/방향 · **우측 1방향 + flip**  ->  ~36
                                                    합계  약 98~165 gen
```

잔여 1277(2026-09-10) 이므로 여유는 있다. 다만 **재추첨이 비싸다** —
환경은 한 호출에 후보 4장이었는데 캐릭터 state 는 1장에 20~40 gen 이다.
🔴 **그래서 캐릭터는 「여러 장 뽑아 고른다」가 아니라 「한 장을 잘 뽑는다」 공정이다.**
문구를 먼저 세우는 것이 환경보다 훨씬 중요해진다.

### ✅ 첫 실호출에서 확정된 것 (2026-09-10 · dark_blade 앵커 · 2 gen)

§7 은 스키마만 읽고 적은 것이었다. 한 번 불러서 절반이 검증됐다.

| 적어 뒀던 것 | 실제 |
|---|---|
| v3 = 2~9 gen | ✅ **2 gen** (하한) |
| size 64 가능 | ✅ 64x64 캔버스 · 그림 세로 61px = **1.9유닛** (목표 2유닛) |
| 팔레트는 후처리로 집행 | ✅ 평균 ΔE **5.5** · 상위5% 8.7 — 파생 경로 관측 범위 안. **10/10단 사용** |
| 8방향이 나온다 | ✅ south/east/north/west + 대각 4 |

### 🔴 그리고 스키마에 없던 것 셋

**① `view="side"` 인데 방향 이름은 top-down 규약 그대로다.**
`south` 가 **정면**이고 `east` 가 순수 측면이다. `side` 는 「눈높이」만 뜻하지
「옆모습만 만든다」가 아니다. 8방향은 그대로 나온다.

**② 순수 측면(`east`)에서 한 손 무기가 몸에 가려 사라진다.**
문구에 `held clear of the body` 를 넣었는데도 그랬다. **8방향 회전 모델은 정면 기준으로
그리고 돌리기 때문에 「측면에서 무기가 보이게」를 보장하지 않는다.**
→ 🔴 **방향 판정은 세 번 바뀌었고 지금은 `south-east` 다** — 아래 「방향 — south-east 로 확정」.

**③ 내용 문구가 약하게 먹는다.** 스키마는 `outline`·`detail` 만 soft guidance 라고
경고했는데 **내용도 그렇다.** 첫 호출에서 세 지시가 다 안 먹었다:

```
held clear of the body   -> 측면에서 대검이 몸에 가렸다
cut short at the hem     -> 긴 망토가 나왔다 (채움 66.5%, 방패병 71% 에 근접)
face never visible       -> 투구에 눈이 그려졌다
```

📌 **셋 다 「하지 마라」에 가까운 말이었다.** `cut short`·`never visible` 은 형태가 아니라
제한이다. 2차에서 **「무엇이 보이는가」로 바꿔** 다시 뽑았다 —
`a smooth faceless helm` · `close-fitting dark armour ending at the waist, bare legs below`.
환경에서 얻은 W4(부정문을 긍정문으로)가 캐릭터 경로에서도 같다.

⚠️ 문구 **순서**도 바꿨다. 1차는 정체성 어휘가 뒤에 몰려 있었다 —
PixelLab 은 길면 희석되는 모델이므로 **가장 중요한 것을 앞에** 둔다.

### 🔴 방향 — `south-east` 로 확정 (2026-09-15 · 세 번째 판정)

```
09-10 1차  east 에서 대검이 몸에 가려 사라진다             -> south-east
09-10 2차  계정 자산 IoU 로 재 보니 east 가 더 잘 갈린다   -> east        (활vs방패 0.37)
09-15 3차  east 에서는 손 앵커가 안 잡힌다                 -> south-east  (현행)
```

2차는 **폼 분별**을 봤고, 3차는 **무기를 손에 붙이는 층**을 봤다(무기 분리 · `08-silhouette §1-C`).
순측면에서는 **먼 팔이 몸에 가려** 검출이 「가장 앞으로 나온 점」만 준다 — 그 점이 자세마다
몸통 앞면이었다가 주먹이었다가 해서, 클립당 보정값(`handOffset`)이 키의 절반(39px)씩 갈렸다.

```
east        키 32/66(48%) · 0키 상태 3개(Dash·Run·Dead) · 검출점이 자세마다 다른 부위
south-east  키 53/66(80%) · 0키 상태 없음 · 일관되게 오른손
```

근거: `Docs/devlog/2026-09-15.md` §6.

📌 2차에서 얻은 교훈은 그대로 산다 — **한 장으로 각도를 판정하면 그 장의 결함을 각도의 성질로 읽는다.**
2차는 「east 에서 대검이 사라진다」가 그림의 자세 결함이었음을 밝혔고, 3차는 **9상태 전부**를 재서 정했다.

🔴 **2차의 근거(폼 분별 IoU)는 SE 에서 아직 안 쟀다.** SE 로 옮긴 것은 붉은 기사 한 벌뿐이다.
3/4 은 몸이 정면에 가까워 **폼끼리 실루엣이 닮을 수 있다.** 폼 3벌을 뽑을 때 두 번 잰다 —
① 몸만(무기가 바뀌어도 폼이 읽히나) ② 몸+무기(실제로 보는 것). `Tools/ArtPipeline/measure_silhouette.py`.

**SE 로 오며 굳은 공정** — 문구 실물은 전부 `animation_prompts.md` 에 있다:

| | |
|---|---|
| 문구 | 긍정문 · **멈춘 자세**로 쓴다 · 정체성 어휘를 **앞에, 매번** · `slash`/`arc` 금지(참격이 그림에 구워진다) |
| 공중·대시 | **2단** — `pose_*` 로 자세를 뽑아 한 장 고르고, `loop_*` 로 「몸은 그대로, 망토만」 |
| 시작 프레임 | **문구보다 강하다** — 목표 자세에 가까운 프레임을 `custom_start_frame_base64` 로 |
| 공중 판정 | Jump·Fall 을 **짝으로** 본다 — 키가 같아야 정점에서 안 튄다 |
| 손 앵커 | `hand_anchors.py --min-protrusion 2` (6 은 「팔이 앞으로 스윙」하는 east 기하에 맞춘 값) |
| 발밑 | 상태 사이에서도 맞춘다 — `align_feet.py` |
| 받기 | 번들 `/spritesheet` (생성 중이면 거부 → 큐를 비운 뒤) · 칸 100x96 → 오프셋 (4,2) 로 92x92 |

📌 flip 규약은 그대로다 — 한 방향만 뽑고 `SpriteRenderer.flipX`.

### 🔴 가장 큰 교훈 — **계정에 이미 있는 것을 먼저 봤어야 했다**

앵커를 두 번 뽑아 **4 gen 을 썼는데**, 계정에는 이미 사용자가 웹에서 만든 캐릭터 11개가
있었다 — 붉은 기사(state 4개 그룹 + idle 애니메이션), 금색 방패 폼, 보라 활 폼.
**내가 만들려던 것보다 나은 것이 이미 있었다.**

📌 **`list_characters` 를 첫 호출로 했어야 했다.** 생성 도구를 조사하기 전에
「이미 무엇이 있나」를 묻는 것이 순서다. 환경에서는 이 문제가 없었다 —
그쪽은 처음부터 다 만들었기 때문이고, **캐릭터는 사용자가 이미 손대고 있던 영역**이었다.

### 웹에서 쓴 프롬프트가 내 것보다 나았던 이유

```
hooded knight, faceless, face in shadow      「얼굴 안 보임」을 후드 그림자라는 형태로
side view, facing right, eye level           방향을 문구로 못박음
flat even lighting                            광원 없음(L1)을 도구 어휘로
transparent background, no ground, no shadow
single accent color only                      강조색 하나만
{{Antique shield}}                            무기를 중괄호로 강조
```

내 문구에는 **자세도, 방향도, 조명도 없었다.**
🔑 **`create_character` 는 자세를 `description` 으로 받는다. 비우면 차렷이 나온다** —
같은 장비라도 차렷이면 초상화가 되고 횡스크롤 액션 캐릭터가 안 된다.

⚠️ 다만 `{{Antique shield}}` 는 **안 먹었다** — 금색 폼에 검이 들려 있다.
중괄호 강조가 이 모델에 통하는지는 확인된 바 없다.

### 앵커 규약은 어떻게 되나

| 환경 | 캐릭터 |
|---|---|
| `style_image` = 씬 앵커 | ❌ 없다. 대신 **`style_character_id`** (pro 모드 전용) |
| `style_copy` 로 항목 선택 | ❌ 없다 |
| 후보 4장 → 사람이 고름 | ❌ 1장 |
| 팔레트는 후처리 집행 | ✅ 같다 — `enforce_palette.py` 는 도구 무관이다 |

💡 `create_character_state` 에 **`use_color_palette_from_reference`** 가 있다 —
원본의 색 팔레트로 스냅한다. 후처리 집행과 **겹치지만 대체하지는 않는다**(씬 팔레트가 아니라
원본 캐릭터 팔레트다). 켜면 넷의 색이 서로 붙는데, 우리는 **색으로 안 가르므로 오히려 맞다.**
